# folder_search 가정

원본 `folder-search-agent`(대화형 검색 데모)를 골격 job으로 옮기며 정한 가정이다.

- 업무 정의: Z몰 직원의 질문 하나를 요청 하나로 본다. 대화 이력(멀티턴)은 이어 가지 않는다.
- 검색 폴더는 `make_spec(folder=...)`로 고정하고, 기본은 `samples/folder_search/files/`(합성 Z몰 문서)다. 원본 `files/`의 실제 문서는 옮기지 않았다.
- 반영은 "답변 기록 저장"(`runtime/.../answers.json`)으로 본다. 원본은 화면에 답만 보여 줬다.
- 승인 정책: 근거 검증을 통과한 `completed` 답은 자동 기록, 그 밖은 사람 확인. 원본에 승인 단계가 없어서 가장 가까운 동작을 골랐다.
- 문서끼리 같은 항목의 값이 다르면 `needs_review`로 올린다. 원본에 없던 규칙이며, 검색 결과를 단정하지 않으려고 더했다.
- 폴더에 관련 내용이 없으면 `failed`로 끝낸다(원본은 "찾지 못했다"고 답함).
- 차단(block) 규칙은 원본에 없어서 두지 않았다.
- 답의 숫자는 문서에 적힌 그대로 써야 통과한다(단위 환산한 숫자는 검증기가 돌려보낸다).
- 의미 검색(`semantic_search`)은 임베딩 객체를 넘길 때만 켠다. 기본 평가(`live_check.py`)는 임베딩을 넘기지 않으므로 키워드 검색 + 읽기 도구로 돈다.
- 의미 검색은 `numpy`도 필요하다(`InMemoryVectorStore` 유사도 계산). 골격 `requirements.txt`에 없어 테스트는 numpy가 없으면 검색 부분을 건너뛴다.
- 의미 검색 청크는 원본의 500자 대신 줄 10개 단위로 바꿨다. 근거를 줄 ID로 적게 하려는 것이다.
- PPTX·DOCX·XLSX·PDF는 `markitdown`으로 읽는다. 골격 `requirements.txt`에는 없어서 이 job의 `requirements.txt`에 넣었다. 없으면 오피스 파일은 목록에서 빠지고, 정리 요청은 입력 로더가 설치 안내와 함께 끊는다.
- 공식 평가(`live_check.py`)는 `DEFAULT_MODEL`(openai:gpt-6-luna)을 쓴다. 시연(`run.py --live`)은 `.env`의 `LLM`으로 모델을 바꿀 수 있고, `OPENAI_API_KEY`가 있으면 OpenAI 임베딩으로 의미 검색을 켠다(`settings.py`).

## 두 번째 뇌 정리 (추가)

- 정리 요청은 `{"organize": "<폴더 기준 상대경로>"}`, 질문은 `{"question": ...}`이다. 하나의 job, 하나의 결과 형식(`SearchAnswer.note`)으로 둘 다 받는다.
- 분류는 PARA 네 가지(프로젝트·영역·자료·보관)로 고정했다. 사용자가 분류 체계를 정하지 않아 가장 널리 쓰이는 방식을 골랐다.
- 노트는 `brain/<분류>/<원본 파일명>.md` 하나다. 원본 하나에 노트 하나로 보고, 노트 이름을 원본 파일명으로 해서 `[[링크]]`가 노트가 아직 없어도 깨지지 않게 했다.
- 노트에는 AI가 쓴 요약·핵심 줄과 함께 markitdown 변환 원문 전체를 넣는다. 노트만 열어도 원문을 볼 수 있게 하려는 것이다.
- 핵심 줄(evidence)은 정리 대상 문서의 줄만 허용한다. 요약의 숫자는 인용한 줄이 아니라 대상 문서 전체의 숫자와 대조한다(요약은 문서 전체를 다루므로).
- 이미 노트가 있는 문서를 다시 정리하면 사람 확인으로 올린다. 덮어쓰기는 이전 정리를 지우는 일이라 자동으로 하지 않는다. 새 차단 규칙은 두지 않았다.
- 질문에 답할 때 근거는 언제나 원본 파일이다. 노트는 AI가 만든 2차 자료라서 검증 기준으로 쓰지 않는다.
- 원본 위치는 PPT는 `<!-- Slide number: N -->`, 엑셀은 `## 시트명` 표시로 찾는다(markitdown 0.1.9 출력 형식). PDF·워드는 줄 ID만 남긴다.
- 시연(`run.py --organize`)은 덮어쓰기 승인 요청에 자동으로 승인한다. 평가 사례는 승인 입력을 사례에 적어 둔다.
